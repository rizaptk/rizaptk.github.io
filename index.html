The engine

HakoDB is my embedded document database in Rust. It runs inside the app, like SQLite: no server, no daemon. Open a file, ship it. I built the hard parts in: vector search, graph traversal, serializable transactions, ChaCha20-Poly1305 encryption at rest. And a flat C ABI underneath, so any language can embed it.

  • Fluent queries filters, cursors, projections, aggregates, indexes built in the background.
  • Vector + graph HNSW nearest-neighbor, BFS and weighted Dijkstra over document references.
  • Zero-copy reads about 18× faster on deeply nested documents.

Sync when you need it

Local-first by default; replication is opt-in. Two planes, pick per deployment.

Peers discover each other with mDNS and replicate WAL deltas behind room keys. No server on the network.

Offline clients converge through a WebSocket hub that micro-batches writes in 5 ms. One replica set per room.

Inside one process, hakocluster fans reads across replicas and routes every write to a single designated writer, with operator-driven failover.

The org

One engine, one namespace, fifteen repos, all MIT. These three carry the product.

hakodb The engine itself. In-process document storage with vector and graph search, a flat C ABI, and fair benchmarks against SQLite and Turso. github ↗docs ↗
hakobackend The HTTP gateway. Plug an engine in, get query and sync over plain REST, with a TypeScript client ready to go. github ↗docs ↗
hakocloudserver The sync hub. A standalone cloud server with an admin console: thousands of offline clients converge into one replica set. github ↗docs ↗

Also in the org: hakocli, hakocluster, hakobalancer, hakomcp, the Go, JS, Pascal and Tauri SDKs, and C++ benchmarks. Full documentation lives at hakodb.github.io.

Agents plug in

hakomcp speaks the Model Context Protocol over stdio. Collections become resources; queries, vector search and graph traversal become agent tools. A model can run RAG against a local database.
